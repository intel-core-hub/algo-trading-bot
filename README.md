# algo-trading-bot

暗号資産市場向けの自動売買戦略の構築・検証プロジェクト。

## スコープと役割分担

- **ここで作るもの**: 相場データ取得、特徴量/シグナル生成、バックテスト、リスク管理ロジック。
- **ユーザー側で行うこと**: 実際の取引所APIキー発行・保管、実資金での発注実行。
  自動発注コードはテストネット/ペーパートレード止まりとし、実弾運用は検証が十分に固まってから
  ユーザー自身の判断・操作で行う。

## 進め方

1. `src/data.py` — ccxtで公開データ(OHLCV)を取得しキャッシュ(ページングして長期履歴も取得可能。
   `python src/data.py <symbol> <timeframe> <total_bars>` でCLI実行可能)
2. `strategies/` — ルールベースの戦略ロジック(MAクロス/モメンタム/平均回帰/トレンドフォロー)
3. `src/backtest.py` — 自前の軽量バックテストエンジン。手数料・スリッページを考慮
4. `backtests/run_baseline.py` — 単純なtrain/test(in-sample/out-of-sample)分割で検証
5. `src/walk_forward.py` / `backtests/run_walk_forward.py` — ローリングwalk-forwardで
   パラメータ再最適化しながらout-of-sample検証(複数銘柄対応)
6. `src/features.py` / `backtests/run_ml_signal.py` — 特徴量エンジニアリング +
   RandomForest分類器ベースのシグナルをwalk-forwardで検証
7. `backtests/run_timeframe_sweep.py` — 同じ戦略群を1h/4h/日足で横並び比較
8. `strategies/funding_contrarian.py` / `backtests/run_funding_signal.py` — 価格以外の
   データ(無期限先物の資金調達率)ベースの逆張りシグナル
9. `backtests/run_portfolio.py` — 複数戦略の等ウェイト組み合わせとリターン相関の検証
10. `src/risk.py` / `backtests/run_risk_managed.py` — ボラティリティ・ターゲティングと
    ドローダウン・ストップのリスク管理オーバーレイ
11. `strategies/funding_carry.py` / `backtests/run_funding_carry.py` — 現物ロング+
    無期限先物ショートのデルタニュートラル・キャリー(価格方向を予測しない)
12. `src/execution.py` / `live/check_and_trade_carry.py` — ファンディング・キャリーの
    テストネット/ペーパートレード発注スケルトン(デフォルトdry-run、実資金は対象外)

### 現状の結果 (2026-09-08時点)

これまでに検証した内容(すべてBTC/USDT・ETH/USDT、手数料10bps+スリッページ5bps込み):

1. **単純なtrain/test分割** (`run_baseline.py`, 1h足): MAクロス・モメンタム・平均回帰の
   3戦略とも train/test 両方 buy-and-hold に負けた。特にモメンタムは取引回数が多く
   コスト負けが大きい。
2. **walk-forward最適化** (`walk_forward.py` / `run_walk_forward.py`, 1h足2.3年、
   train2000本/test500本ローリング36 fold): train窓でのグリッドサーチ最良パラメータを
   test窓に適用してもout-of-sample連結リターンは-73%〜-96%とさらに悪化。fold毎の
   ベストパラメータも安定せず、**ナイーブな「train窓のSharpe最大化」は過学習しやすい**
   ことを確認。train窓を4分割し(平均-標準偏差)を最大化する`robust_selector`に
   変えても-65%〜-95%と大勢は変わらず。
3. **長期トレンドフォロー** (`strategies/trend_following.py`, 日足換算50/200日MAクロス):
   取引回数を数回まで激減させ手数料の影響をほぼ消しても、なお buy-and-hold に負けた
   → **コストの問題ではなく方向予測自体が外れている**ことを確認。
4. **MLシグナル** (`src/features.py` / `run_ml_signal.py`, RandomForest 3クラス分類):
   予測ホライズンと保有期間を一致させる修正(最初は毎バー再予測でコスト負けするバグが
   あった)後もout-of-sample -65.95%/-96.47%。方向的中率は train~50%・test~36%
   (ランダムは33%)でほぼ運と同じ、特徴量重要度もボラティリティ系のみが上位。
5. **時間足スイープ** (`run_timeframe_sweep.py`, 1h/4h/日足): 直近850本の日足だけで
   見るとMAクロス・モメンタムが逆にbuy-and-holdに大勝ち(ETHモメンタムtest +250%等)
   したが、**日足履歴を2000本(≈5.5年、2021-2026、複数の強気/弱気相場を含む)に
   拡張して再検証すると勝ちが消え、元の「エッジなし」の結論に戻った**。
   小サンプル(850本≒2年強)でのbacktest結果は簡単に過学習・偶然の勝ちを生む、
   という重要な教訓。

**中間結論**: ルールベース4種、walk-forwardでのnaive/robust再最適化、RandomForest分類器、
3つの時間足のいずれも、手数料控除後に一貫したエッジを示せなかった。また日足の小サンプルで
見えた「勝ち」も長期データでは再現しなかった。単純な価格ベースの特徴量だけでは、この市場に
この粒度の方向優位性は乗っていない可能性が高い。そこで以下の3方向を追加検証した。

6. **価格以外のデータ: ファンディングレート逆張り** (`funding_contrarian.py` /
   `run_funding_signal.py`, BTC/ETH無期限先物の資金調達率をZスコア化し極端値で逆張り):
   train/testとも buy-and-hold に負けた(BTC train -42.99%/test -42.51%、
   ETH train -52.15%/test -15.47%)。価格以外のデータに切り替えても、この単純な
   逆張りロジックではエッジは出なかった。
7. **複数戦略の組み合わせ** (`run_portfolio.py`, MAクロス/モメンタム/平均回帰/
   トレンドフォローを等ウェイト平均): 戦略間リターン相関は確かに低い/マイナス
   (例: mean_reversion対momentumは-0.6程度)で分散効果の余地はあったが、
   ポートフォリオの成績は個別戦略の中央値程度〜やや悪い水準にとどまった
   (BTC test: 個別+3.92%〜-66.40%に対しポートフォリオ-38.12%)。さらに複数シグナルを
   毎バー平均すると、方向を変えていなくても細かくサイズが変わり続けるため取引回数が
   桁違いに増える(train2577回等)。**個々に負のエッジしかない戦略は、相関が低くても
   組み合わせただけでは黒字化しない**(分散はリスク低減の道具であってアルファを
   生む道具ではない)ことを確認。
8. **リスク管理オーバーレイ** (`src/risk.py` / `run_risk_managed.py`,
   ボラティリティ・ターゲティング+ドローダウン・ストップ): buy-and-holdや
   trend_followingに適用したところ、年率ボラティリティ・最大ドローダウンは
   狙い通り大幅に低下した(例: ETH train buy&holdの年率ボラ68.98%→9.04%、
   最大DD-65.28%→-22.36%)。ただし当初はサイズを毎バー連続的に更新したため
   取引コストが爆発し(train9783回)、リターンが大きく悪化する副作用が出た。
   `rebalance_every`パラメータで更新頻度を1日1回に落とすことでコストは
   1桁減り(train493回)、リスク低減効果は保ちつつ副作用を大幅に軽減できた。
   **リスク管理層は「勝てないシグナルを勝たせる」ものではないが、同じ(負けている)
   エクスポージャーでもドローダウンを大きく抑えられる**ことを確認できた。これは
   実運用に必須の基盤として独立した価値がある。

**方向性予測から「キャリー(裁定的な収益源)」への転換**: ここまでの8項目はすべて
「価格の方向を当てる」試みだったが、方向性を一切予測しない
**ファンディング・キャリー**(`strategies/funding_carry.py` /
`backtests/run_funding_carry.py`)を検証したところ、プロジェクト全体で唯一の
明確に頑健なプラス結果が出た。

9. **ファンディング・キャリー(初期検証)** (現物ロング+無期限先物ショートの
   デルタニュートラル。資金調達率がプラスの間、ショート側として資金調達を受け取り
   続ける): 資金調達率履歴を5.5年(2021-03〜2026-09、2021強気相場・2022弱気相場を
   含む)に拡張して検証した結果、フィルタなしで常に建てっぱなしにする`always_on_carry`
   が、BTC/ETH・train/testの全4パターンでプラス、Sharpe 11〜20、最大ドローダウン2%未満
   という、これまでのどの戦略とも一線を画す結果になった。ただしこの初期版は
   資金調達率をそのままリターンとみなす簡略化モデル(現物と先物は完全に連動する
   前提)だったため、より厳密に検証し直した(下記10)。

10. **ファンディング・キャリー(ベーシスリスクを反映した再検証・銘柄拡張)**
    (`run_funding_carry_backtest`, BTC/ETH/SOL/BNBの4銘柄、両レッグ$1ずつ=投入資本$2
    に対するリターンとして計算): 現物と無期限先物の実際の価格差変動(ベーシスリスク)を
    反映させたところ、**一度は当初の結果が大きく崩れる誤検知が起きた**。無期限先物の
    funding rate APIが返す"mark price"(清算判定用の複数取引所指数)を先物価格として
    使ったところ、実際には取引できない参照価格であるため現物とのベーシスの標準偏差が
    1.58%/8hにも達し、これによる見せかけのボラティリティ・ドラッグでBTCの結果が
    +20%→-3%に反転してしまった。無期限先物の**実際の約定価格**(mark priceではなく
    fetch_ohlcv market_type="future")に差し替えたところベーシスの標準偏差は0.04%/8h
    まで下がり、想定通りの結果に戻った。**バックテストで「価格」として何を使うかの
    データ品質が、結論そのものを左右しうる**という重要な教訓。

    修正後の結果: BTC/ETHは引き続き頑健にプラス
    (BTC train: return+21.52% sharpe+9.58 max_dd-0.34%、
    BTC test: return+3.31% sharpe+5.42 max_dd-0.23%、ETHもほぼ同水準)。
    一方SOL/BNBは一貫しない(SOL train+3.96%/test-0.67%、BNBはtrain期間の平均資金調達率
    がマイナスだったため train-9.39%)。**このエッジはBTC/ETHのような最も流動性の高い
    銘柄でこそ頑健で、アルトコインには単純に一般化できない**。また証拠金/清算リスクの
    目安として先物価格の急変動幅を計測したところ、BTC最大8h変動11.88%・7日騰落
    +37.83%/-34.34%に対し、SOLは最大8h変動29.20%・7日騰落+85.55%/-62.00%と桁違いに
    大きく、アルトコインは証拠金バッファ要件も厳しいことが分かった。
    直近7日平均の資金調達率がプラスの時だけ建てる`conditional_carry`(フィルタあり)は
    引き続き頻繁な出入りでコスト負けし、常に建てておく`always_on`より劣った。
    なお平均資金調達率(年率換算)はtrain期間+10%前後→test期間+3〜4%(BTC/ETH)と
    縮小傾向にあり、このキャリー機会自体が市場参加者の増加で年々薄くなっている
    可能性が高い。

    **依然としてこのバックテストがモデル化していないリスク**: (i) 証拠金・清算リスク
    (先物ショート脚は価格急騰時に追証・強制清算のリスクがあり、現物・先物が別ウォレット
    の場合ポートフォリオマージンが無いと経済的にヘッジ済みでも証拠金不足になりうる)、
    (ii) 現物・先物を同時運用する実行上の複雑さ、(iii) cost_bps=30は概算で実際の
    手数料体系に依存、(iv) エッジが縮小傾向。

11. **テストネット/ペーパートレード発注スケルトン** (`src/execution.py` /
    `live/check_and_trade_carry.py`): 直近7日平均の資金調達率がプラスなら建てる/
    維持、マイナスに転じたら手仕舞う(頻繁な出入りはコスト負けすると分かっているので
    1日1回程度の実行を想定)。**デフォルトはdry-run**で実際の注文は一切送信されず、
    意図する注文をログ出力するのみ。`--live`を付けても`.env`にテストネット専用の
    APIキー(Binance Spot TestnetとFutures Testnetは別アカウント・別キー)が無ければ
    実行時エラーになる。dry-runでの動作(公開データのみ使用)は実際に確認済み
    (2026-09-08時点でBTC/USDT: 資金調達率+0.0046%/interval → enter判定)。
    **テストネットでの実発注は未検証**(APIキーを持っていないため) — 利用する前に
    必ず少額のテストネット資金で動作確認すること。実資金のキーは絶対に使わないこと。

**現時点までの全体結論**: 「価格の方向を当てる」系のアプローチ(ルールベース4戦略、
walk-forward最適化、ML分類器、3時間足、ファンディング逆張り、複数戦略の組み合わせ)は
すべて一貫してエッジを示せなかった一方、方向性を予測しない**ファンディング・キャリーは
BTC/ETHで5.5年・train/testの全パターンで頑健にプラス**という、質的に異なる結果になった
(ただし当初の結果は先物価格データの選び方によるアーティファクトを含んでおり、修正後も
数字は縮小した)。SOL/BNBには単純に一般化できず、アルトコインは証拠金リスクも大きい。
リスク管理層(ボラティリティ・ターゲティング、ドローダウン・ストップ)も狙い通りに機能する
ことを確認済み。テストネット向けの発注コード(dry-run動作確認済み、実発注は未検証)も
用意した。

**実資金投入前に、ユーザー側で確認・準備が必要な残り項目**:
- `.env`にBinance Spot/Futures両テストネットのAPIキーを発行・設定し、
  `live/check_and_trade_carry.py --live`で実際にテストネット注文が通ることを確認する
- 現物・先物ウォレット間のポートフォリオマージン設定(証拠金効率とヘッジ時の
  追証リスクに直結)を、利用する取引所の実際の仕様で確認する
- cost_bps=30の前提を、実際に使う取引所・アカウントの手数料ティアで検証し直す
- 十分な期間、テストネット/ペーパートレードで運用し、想定通りの動きになるか確認する

## セットアップ

```bash
python -m venv .venv
.venv/Scripts/pip install -r requirements.txt
```

APIキーが必要になった場合は `.env` に置く(gitignore済み)。マーケットデータ取得自体は
公開エンドポイントのみを使うため、当面はAPIキー不要で進められる。
