# algo-trading-bot

暗号資産市場向けの自動売買戦略の構築・検証プロジェクト。

## スコープと役割分担

- **ここで作るもの**: 相場データ取得、特徴量/シグナル生成、バックテスト、リスク管理ロジック。
- **ユーザー側で行うこと**: 実際の取引所APIキー発行・保管、実資金での発注実行。
  自動発注コードはテストネット/ペーパートレード止まりとし、実弾運用は検証が十分に固まってから
  ユーザー自身の判断・操作で行う。

## 進め方

1. `src/data.py` — ccxtで公開データ(OHLCV)を取得しキャッシュ(ページングして長期履歴も取得可能。
   `python src/data.py <symbol> <timeframe> <total_bars>` でCLI実行可能)
2. `strategies/` — ルールベースの戦略ロジック(MAクロス/モメンタム/平均回帰/トレンドフォロー)
3. `src/backtest.py` — 自前の軽量バックテストエンジン。手数料・スリッページを考慮
4. `backtests/run_baseline.py` — 単純なtrain/test(in-sample/out-of-sample)分割で検証
5. `src/walk_forward.py` / `backtests/run_walk_forward.py` — ローリングwalk-forwardで
   パラメータ再最適化しながらout-of-sample検証(複数銘柄対応)
6. `src/features.py` / `backtests/run_ml_signal.py` — 特徴量エンジニアリング +
   RandomForest分類器ベースのシグナルをwalk-forwardで検証
7. `backtests/run_timeframe_sweep.py` — 同じ戦略群を1h/4h/日足で横並び比較
8. `strategies/funding_contrarian.py` / `backtests/run_funding_signal.py` — 価格以外の
   データ(無期限先物の資金調達率)ベースの逆張りシグナル
9. `backtests/run_portfolio.py` — 複数戦略の等ウェイト組み合わせとリターン相関の検証
10. `src/risk.py` / `backtests/run_risk_managed.py` — ボラティリティ・ターゲティングと
    ドローダウン・ストップのリスク管理オーバーレイ
11. `strategies/funding_carry.py` / `backtests/run_funding_carry.py` — 現物ロング+
    無期限先物ショートのデルタニュートラル・キャリー(価格方向を予測しない)
12. `src/execution.py` / `live/check_and_trade_carry.py` — ファンディング・キャリーの
    テストネット/ペーパートレード発注スケルトン(デフォルトdry-run、実資金は対象外。
    エントリー前の1倍レバレッジ強制・2レッグ発注の失敗時ロールバック・状態照合・
    手仕舞い数量は常に取引所の実残高から取り直す・spot_only復旧・OS非依存の排他ロック・
    出入り頻度のクールダウン付き)
13. `tests/` — pytestによる自動テスト(`python -m pytest tests/`、50ケース)

### 現状の結果 (2026-09-08時点)

これまでに検証した内容(すべてBTC/USDT・ETH/USDT、手数料10bps+スリッページ5bps込み):

1. **単純なtrain/test分割** (`run_baseline.py`, 1h足): MAクロス・モメンタム・平均回帰の
   3戦略とも train/test 両方 buy-and-hold に負けた。特にモメンタムは取引回数が多く
   コスト負けが大きい。
2. **walk-forward最適化** (`walk_forward.py` / `run_walk_forward.py`, 1h足2.3年、
   train2000本/test500本ローリング36 fold): train窓でのグリッドサーチ最良パラメータを
   test窓に適用してもout-of-sample連結リターンは-73%〜-96%とさらに悪化。fold毎の
   ベストパラメータも安定せず、**ナイーブな「train窓のSharpe最大化」は過学習しやすい**
   ことを確認。train窓を4分割し(平均-標準偏差)を最大化する`robust_selector`に
   変えても-65%〜-95%と大勢は変わらず。
3. **長期トレンドフォロー** (`strategies/trend_following.py`, 日足換算50/200日MAクロス):
   取引回数を数回まで激減させ手数料の影響をほぼ消しても、なお buy-and-hold に負けた
   → **コストの問題ではなく方向予測自体が外れている**ことを確認。
4. **MLシグナル** (`src/features.py` / `run_ml_signal.py`, RandomForest 3クラス分類):
   予測ホライズンと保有期間を一致させる修正(最初は毎バー再予測でコスト負けするバグが
   あった)、さらに後日train窓末尾のラベルリーク(下記13で発見)を修正した後の数値で
   out-of-sample BTC -42.23%/ETH -94.72%。方向的中率はほぼ運と同じで、特徴量重要度も
   ボラティリティ系のみが上位という状況に変化はない。
5. **時間足スイープ** (`run_timeframe_sweep.py`, 1h/4h/日足): 直近850本の日足だけで
   見るとMAクロス・モメンタムが逆にbuy-and-holdに大勝ち(ETHモメンタムtest +250%等)
   したが、**日足履歴を2000本(≈5.5年、2021-2026、複数の強気/弱気相場を含む)に
   拡張して再検証すると勝ちが消え、元の「エッジなし」の結論に戻った**。
   小サンプル(850本≒2年強)でのbacktest結果は簡単に過学習・偶然の勝ちを生む、
   という重要な教訓。

**中間結論**: ルールベース4種、walk-forwardでのnaive/robust再最適化、RandomForest分類器、
3つの時間足のいずれも、手数料控除後に一貫したエッジを示せなかった。また日足の小サンプルで
見えた「勝ち」も長期データでは再現しなかった。単純な価格ベースの特徴量だけでは、この市場に
この粒度の方向優位性は乗っていない可能性が高い。そこで以下の3方向を追加検証した。

6. **価格以外のデータ: ファンディングレート逆張り** (`funding_contrarian.py` /
   `run_funding_signal.py`, BTC/ETH無期限先物の資金調達率をZスコア化し極端値で逆張り):
   train/testとも buy-and-hold に負けた(BTC train -42.99%/test -42.51%、
   ETH train -52.15%/test -15.47%)。価格以外のデータに切り替えても、この単純な
   逆張りロジックではエッジは出なかった。
7. **複数戦略の組み合わせ** (`run_portfolio.py`, MAクロス/モメンタム/平均回帰/
   トレンドフォローを等ウェイト平均): 戦略間リターン相関は確かに低い/マイナス
   (例: mean_reversion対momentumは-0.6程度)で分散効果の余地はあったが、
   ポートフォリオの成績は個別戦略の中央値程度〜やや悪い水準にとどまった
   (BTC test: 個別+3.92%〜-66.40%に対しポートフォリオ-38.12%)。さらに複数シグナルを
   毎バー平均すると、方向を変えていなくても細かくサイズが変わり続けるため取引回数が
   桁違いに増える(train2577回等)。**個々に負のエッジしかない戦略は、相関が低くても
   組み合わせただけでは黒字化しない**(分散はリスク低減の道具であってアルファを
   生む道具ではない)ことを確認。
8. **リスク管理オーバーレイ** (`src/risk.py` / `run_risk_managed.py`,
   ボラティリティ・ターゲティング+ドローダウン・ストップ): buy-and-holdや
   trend_followingに適用したところ、年率ボラティリティ・最大ドローダウンは
   低下した。ただし当初はサイズを毎バー連続的に更新したため取引コストが爆発し
   (train9783回)、`rebalance_every`パラメータで更新頻度を1日1回に落として
   コストを1桁減らした(train493回)。

   **この項目には、後日(下記13)発覚した重大な自己バグがあった**: 最初に報告した
   「ETH train buy&holdの年率ボラ68.98%→9.04%、最大DD-65.28%→-22.36%」という
   劇的な改善は、`apply_drawdown_stop`のバグ(ブレイク発生後にピークエクイティが
   凍結されたまま二度と更新されず、クールダウン明けの初手で即座に再ブレイク判定
   されてしまい、事実上「一度ブレイクしたら二度とポジションを取らない」という
   壊れた回路になっていた)による見かけ上の数値だった。ずっとノーポジのままなら
   ボラもドローダウンもほぼゼロに見えるのは当然で、意図していた「一時停止して
   落ち着いたら再開する」サーキットブレーカーにはなっていなかった。
   このバグは別セッションで発見・修正され(ピークエクイティをクールダウン明けに
   凍結中の水準へリセット)、今回さらに`cooldown_bars=0`のエッジケース漏れも
   追加修正した(下記13、テスト9件で回帰確認済み)。

   **修正後の実際の効果**(rebalance_every=1日、max_drawdown=20%、cooldown=24本):
   ボラティリティ・ターゲティング単体でおおよそ年率ボラを3〜4割圧縮する効果は
   実在するが、その上にドローダウン・ストップを重ねても追加の改善はごくわずか
   (例: BTC train ann_vol 32.82%→32.65%、max_dd -33.50%→-34.69%とほぼ横ばい、
   ETH train ann_vol 37.25%→36.83%、max_dd -56.82%→-54.50%とわずかな改善)。
   **「勝てないシグナルを勝たせる」ものではない、という結論自体は変わらないが、
   ドローダウン・ストップの効果は当初報告よりずっと小さく、主な効果は
   ボラティリティ・ターゲティングの方から来ている**、というのが正しい結論。

**方向性予測から「キャリー(裁定的な収益源)」への転換**: ここまでの8項目はすべて
「価格の方向を当てる」試みだったが、方向性を一切予測しない
**ファンディング・キャリー**(`strategies/funding_carry.py` /
`backtests/run_funding_carry.py`)を検証したところ、プロジェクト全体で唯一の
明確に頑健なプラス結果が出た。

9. **ファンディング・キャリー(初期検証)** (現物ロング+無期限先物ショートの
   デルタニュートラル。資金調達率がプラスの間、ショート側として資金調達を受け取り
   続ける): 資金調達率履歴を5.5年(2021-03〜2026-09、2021強気相場・2022弱気相場を
   含む)に拡張して検証した結果、フィルタなしで常に建てっぱなしにする`always_on_carry`
   が、BTC/ETH・train/testの全4パターンでプラス、Sharpe 11〜20、最大ドローダウン2%未満
   という、これまでのどの戦略とも一線を画す結果になった。ただしこの初期版は
   資金調達率をそのままリターンとみなす簡略化モデル(現物と先物は完全に連動する
   前提)だったため、より厳密に検証し直した(下記10)。

10. **ファンディング・キャリー(ベーシスリスクを反映した再検証・銘柄拡張)**
    (`run_funding_carry_backtest`, BTC/ETH/SOL/BNBの4銘柄、両レッグ$1ずつ=投入資本$2
    に対するリターンとして計算): 現物と無期限先物の実際の価格差変動(ベーシスリスク)を
    反映させたところ、**一度は当初の結果が大きく崩れる誤検知が起きた**。無期限先物の
    funding rate APIが返す"mark price"(清算判定用の複数取引所指数)を先物価格として
    使ったところ、実際には取引できない参照価格であるため現物とのベーシスの標準偏差が
    1.58%/8hにも達し、これによる見せかけのボラティリティ・ドラッグでBTCの結果が
    +20%→-3%に反転してしまった。無期限先物の**実際の約定価格**(mark priceではなく
    fetch_ohlcv market_type="future")に差し替えたところベーシスの標準偏差は0.04%/8h
    まで下がり、想定通りの結果に戻った。**バックテストで「価格」として何を使うかの
    データ品質が、結論そのものを左右しうる**という重要な教訓(このタイムスタンプ突き合わせ
    自体にもさらに1段細かい問題があったことが下記13で判明し、追加修正した)。

    修正後の結果(下記13の一連の修正: 最終手仕舞いコスト計上、cost_bpsの資本基準統一、
    タイムスタンプ完全一致でのつき合わせ、をすべて反映した最新値): BTC/ETHは引き続き
    頑健にプラス
    (BTC train: return+21.61% sharpe+9.55 max_dd-0.34%、
    BTC test: return+3.24% sharpe+7.14 max_dd-0.22%、ETHもほぼ同水準)。
    一方SOL/BNBは一貫しない(SOL train+3.96%/test-0.86%、BNBはtrain期間の平均資金調達率
    がマイナスだったため train-9.21%)。**このエッジはBTC/ETHのような最も流動性の高い
    銘柄でこそ頑健で、アルトコインには単純に一般化できない**。また証拠金/清算リスクの
    目安として先物価格の急変動幅を計測したところ、BTC最大8h変動11.88%・7日騰落
    +37.83%/-34.34%に対し、SOLは最大8h変動29.20%・7日騰落+85.55%/-62.00%と桁違いに
    大きく、アルトコインは証拠金バッファ要件も厳しいことが分かった。
    直近7日平均の資金調達率がプラスの時だけ建てる`conditional_carry`(フィルタあり)は
    引き続き頻繁な出入りでコスト負けし、常に建てておく`always_on`より劣った。
    なお平均資金調達率(年率換算)はtrain期間+10%前後→test期間+3〜4%(BTC/ETH)と
    縮小傾向にあり、このキャリー機会自体が市場参加者の増加で年々薄くなっている
    可能性が高い。

    **依然としてこのバックテストがモデル化していないリスク**: (i) 証拠金・清算リスク
    (先物ショート脚は価格急騰時に追証・強制清算のリスクがあり、現物・先物が別ウォレット
    の場合ポートフォリオマージンが無いと経済的にヘッジ済みでも証拠金不足になりうる)、
    (ii) 現物・先物を同時運用する実行上の複雑さ、(iii) 実際の取引所手数料体系、
    (iv) エッジが縮小傾向。

11. **テストネット/ペーパートレード発注スケルトン(初期版)** (`src/execution.py` /
    `live/check_and_trade_carry.py`): 直近7日平均の資金調達率で毎回enter/exitを
    判断する初期版を作ったが、外部レビューで重大な欠陥を複数指摘された(下記12)。

12. **1回目の外部レビューを受けた修正**: 実運用に進める前に、このプロジェクトの外部
    レビューを受けたところ、以下5点の欠陥が指摘された。いずれも妥当な指摘だったため
    修正した。
    - **2レッグ発注が原子的でない**: 現物と先物を同時に約定させることはできないため、
      片方だけ成功する状態が起こりうる。`place_carry_orders`/`close_carry_orders`を、
      失敗時に「常に低リスクな現物ロングのみが残る」順序(エントリーは現物→先物、
      イグジットは先物→現物)で組み直し、先物側が失敗したら現物を巻き戻す処理を追加。
      巻き戻し自体が失敗した場合のみ`needs_manual_intervention`フラグを立てて
      以降の自動売買を止めるようにした。
    - **状態ファイル(JSON)を無条件に信用していた**: `execution.reconcile_state`を
      追加し、`--live`実行時は毎回、実際の現物残高・先物建玉を取得して状態ファイルと
      突き合わせ、食い違いがあれば発注前に停止するようにした。
    - **バックテストで勝ったalways_onと、liveの毎日判定ロジックが不一致だった**:
      直近7日平均で毎回enter/exitするconditional_carryはOOSでコスト負けすると
      既に判明していたのに、live版はまさにそのロジックだった。`--min-hold-days`
      (デフォルト14日)のクールダウンを追加し、直近のenter/exitから一定期間は
      反対方向のアクションを取らないようにして、頻繁な出入りを抑制した。
    - **自動テストが無かった**: `tests/`にpytestを追加した。`requirements.txt`も
      バージョンを固定した。
    - **バックテストの最終手仕舞いコストが未計上だった**: `cost_bps`は片道コストで
      ラウンドトリップは2倍かかる、という前提を明文化した上で、期間終了時に
      建玉が残っている場合はその手仕舞いコストも最終バーに計上するよう
      `src/backtest.py`を修正。

13. **2回目の外部レビュー(zip添付)を受けた追加修正**: さらに別の外部レビューで
    修正案一式(zip)が提供された。すべて鵜呑みにせず1件ずつ差分を確認し、自分でも
    再現・追加検証した結果、**レビュー自体の指摘はほぼ正しかった一方、提案コードの
    中にも新たな不具合を見つけて修正した**。

    採用した修正:
    - **最大ドローダウンの計算漏れ**: `equity_curve.cummax()`だけを基準にすると、
      開始時点のエクイティ1.0そのものが比較対象に入らないため、「1本目のバー自体が
      最大の下落だった」場合のドローダウンが0%と誤って算出されていた
      (`max_drawdown_from_returns`として先頭に1.0を明示的に加えて修正)。
    - **`strategies/trend_following.py`の先読みバイアス**: `resample("1D").last()`
      で作った日足シグナルは、その日の終値が確定する(=1h足がその日の分すべて
      出そろう)までは本当は分からないのに、reindex+ffillで同日の朝から使えて
      しまっていた。`shift(1)`でシグナルの有効化を丸1日遅らせて修正
      (影響は小さく、結論(buy&holdに勝てない)は変わらず)。
    - **`run_ml_signal.py`のラベルリーク**: ラベルは`close.shift(-HORIZON)`で
      HORIZON本先の未来の終値を使うため、train窓の末尾HORIZON本はラベルの一部が
      test窓側の価格を参照してしまっていた(train/test境界をまたぐリーク)。
      train窓の末尾HORIZON本を学習から除外(purge)するよう修正
      (BTCの結果はむしろ改善: oos_return -65.95%→-42.23%。ただし依然として
      買い持ち以下で、結論は変わらず)。
    - **`run_funding_carry.py`のコスト基準の不整合**: リターンは投入資本$2基準
      (0.5倍)で計算しているのに、コストは$1ノーション基準の30bpsをそのまま
      差し引いており、資本基準で見ると実質コストを2倍過大計上していた。
      コストも同じ資本基準に揃えて15bpsに修正(結果はやや改善)。
    - **`apply_drawdown_stop`の`cooldown_bars=0`エッジケース**: ピークエクイティの
      リセットが「クールダウンが明けた瞬間」にしか起きない実装だったため、
      `cooldown_bars=0`だとその分岐を一度も通らずリセットの機会が無いまま
      永久に再トリガーし続ける、という別のバグが残っていた。ブレイク発生時点で
      即座にリセットするよう修正し、回帰テストを追加。

    **レビュー提供コードの中に見つけた新たな不具合(そのままでは採用しなかった/修正して
    採用した)**:
    - `src/execution.py`の`CarryExecutionResult.fully_positioned`: あいまいな注文
      失敗(先物注文がAPI例外を返したが、実際には約定していた)を検知して
      `needs_manual_intervention=True`を立てても、たまたま数量が一致していると
      `fully_positioned`が`True`のままになるケースを実際に再現できた。呼び出し側が
      `if fully_positioned: ... elif needs_manual_intervention: ...`という順で
      分岐すると、要確認フラグを見落として通常のcarry状態として処理してしまう。
      `fully_positioned`が`needs_manual_intervention`のとき必ず`False`を返すよう
      修正し、この具体的なシナリオの回帰テストを追加。
    - `live/check_and_trade_carry.py`の同時実行防止ロック: 提供コードは`fcntl`
      (Unix専用)でロックを取っていたが、**このプロジェクトの開発環境はWindows**
      であり、`fcntl`はWindowsに存在しないため`--live`実行が確実にクラッシュする
      状態だった。`os.open(..., O_CREAT | O_EXCL)`によるOS非依存の排他ロックに
      差し替え、Windows上で実際に動作することを確認した。
    - `backtests/run_funding_carry.py`のタイムスタンプ突き合わせ: 提供コードは
      ffillの代わりにspot/perp/fundingの3系列を「タイムスタンプ完全一致」で
      内部結合していたが、fundingのタイムスタンプにはミリ秒単位のジッターがあり、
      素朴な完全一致では実際に約定日時履歴の**半分近く(BTCで6000行→3225行)が
      無駄に捨てられていた**。ffillの潜在的な取り違えリスクは残しつつも、
      秒単位に丸めてから完全一致で結合することで、データを1行も捨てずに
      同じ安全性を確保できることを確認し、そちらを採用した。

    **それでも未検証・未対応の点**: テストネットでの実際の2レッグ発注は
    (APIキーを持っていないため)一度も実行できていない。ポートフォリオマージンの
    実際の挙動(取引所仕様依存)も未確認。`--min-hold-days`によるクールダウンは
    always_onを近似する応急措置であり、always_on自体をliveで正確に再現している
    わけではない。

14. **3回目の外部レビュー(patch添付)を受けた追加修正**: さらに`.patch`形式で
    修正案一式が提供された。現在のコードとはベースが乖離しており`git apply`は
    そのまま通らなかったため、差分を1件ずつ読んで内容を評価し、価値のある部分だけを
    現在の実装に手で移植した。

    採用した修正:
    - **先物レバレッジの明示設定が無かった**: `place_carry_orders`はこれまで
      取引所口座のデフォルトレバレッジ設定に任せていた。テストネットでも
      デフォルトが5〜20倍等になっていることがあり、「現物+先物の無レバレッジ
      キャリー」のつもりが意図せずレバレッジ付きポジションになり清算リスクが
      跳ね上がりうる。エントリー前に`set_leverage(1, ...)`を明示的に呼ぶよう追加
      (設定自体が失敗した場合は、まだ何の注文も送っていないので安全にそのまま中断)。
    - **手仕舞い数量を状態ファイルの記録に依存していた**: `close_carry_orders`/
      `close_spot_only`は、状態ファイルに記録された数量(`reconcile_state`で
      事前に実残高と照合済みではあるが)を使って手仕舞いサイズを決めていた。
      照合してから発注するまでの間にズレが生じる余地をゼロにするため、
      手仕舞い数量は常にその場で取引所から取り直した実際の保有数量を使うように
      変更(記録値は一切使わない)。あわせて、実ポジションが「現物とショートが
      釣り合ったcarry」に分類できない場合は発注せず停止するチェックを追加。
    - **ML境界purgeロジックの単体テスト化**: `run_ml_signal.py`のtrain/test境界
      purge処理を`purge_training_boundary`という独立関数に切り出し、直接
      テストできるようにした(ロジック自体は前回の修正から変更なし)。
    - **live本体の統合テストが無かった**: `tests/test_live_recovery.py`を追加し、
      `live/check_and_trade_carry.py`をファイルパスから直接importして`_run()`を
      実際に呼び出し、「spot_only復旧は資金調達率取得より優先される」
      「needs_manual_intervention中は取引所に一切問い合わせない」
      「クールダウン中はexit判断がholdに上書きされる」の3点を検証。

    **提案されていたが採用しなかった/別の形で対応した部分**: 取引所エラー
    (`ccxt.ExchangeError`、明示的な拒否)とネットワークエラー(`ccxt.NetworkError`、
    結果があいまい)を区別し、後者の場合だけ自動巻き戻しを止める、という提案が
    あった。既存の実装は例外の種類を見る代わりに、失敗後に**取引所へ実際に
    問い合わせて**ショートポジションの有無を確認してから巻き戻すかどうかを
    決めており(`_fetch_perp_signed_base_amount`)、これは例外の型を手がかりに
    推測するより直接的で頑健な確認方法だと判断し、変更しなかった。

15. **4回目の外部レビュー(patch形式)を受けた追加修正**: `.patch`形式で
    「7件の指摘」が提供されたが、このレビューは3回目までの修正を知らない
    古いコード時点(2回目のzipレビューより前)を基準に作られていたため、
    ほとんどの指摘(spot_only優先処理、状態照合の数量チェック、drawdown-stopの
    ピークリセット、MLラベルリークのpurge化)は既に別の形で対応済みだった。
    その中で唯一、これまで対応していなかった新規の指摘が1件あった。
    - **win_rateがバー単位でトレード単位ではなかった**: `run_backtest`の
      `win_rate`は「ポジションを持っているバーのうちリターンがプラスだった
      割合」であり、entry→exitの1トレード単位の勝率ではなかった。例えば
      +10%,+10%と2バー連続で勝った直後に-50%で決済されるtradeは、バー単位
      では2勝1敗(66%)に見えるが、trade自体は明確な負けである。
      `_closed_trade_returns`を追加し、同符号内のリサイズは同一trade、
      反転は旧tradeの決済+新tradeの建玉として分割集計し、entry→exit単位の
      ネットリターンでwin_rateを計算し直すよう修正(このプロジェクトの
      バックテストで`win_rate`を直接レポートしている箇所は無かったため、
      過去に記載した数値への影響は無い)。

**現時点までの全体結論**: 「価格の方向を当てる」系のアプローチ(ルールベース4戦略、
walk-forward最適化、ML分類器、3時間足、ファンディング逆張り、複数戦略の組み合わせ)は
すべて一貫してエッジを示せなかった一方、方向性を予測しない**ファンディング・キャリーは
BTC/ETHで5.5年・train/testの全パターンで頑健にプラス**という、質的に異なる結果になった
(ただし当初の結果は先物価格データの選び方によるアーティファクトを含んでおり、修正後も
数字は縮小した)。SOL/BNBには単純に一般化できず、アルトコインは証拠金リスクも大きい。
リスク管理層は、当初報告した劇的な効果(ドローダウン・ストップの不具合による見かけ上の
数値)が誤りだったことが判明し、修正後は「ボラティリティ・ターゲティングにはそれなりの
効果があるが、ドローダウン・ストップの追加効果はごくわずか」という、より地味だが正しい
結論に訂正した。テストネット向けの発注コードは4回の外部レビューを経て、レバレッジ管理・
原子性・状態照合・liveロジックの整合性・自動テスト・OS互換性を一通り整備し、バックテスト
エンジンの`win_rate`もトレード単位の正しい定義に修正したが、実際のテストネット発注
そのものは未検証。**4回にわたる外部レビューはいずれも部分的に正しく、かつ提案コードの
中にも新たな不具合を含んでいた** — 「レビューを鵜呑みにしない、必ず自分で再現・検証する」
ことの重要性を、このプロジェクト自体が体現する結果になった。

**現在のステータス: 研究・検証プロトタイプとしては完成。テストネット自動売買ボットとしては
Beta(実発注未検証)。実資金運用の対象では全くない。**

**実資金投入前に、ユーザー側で確認・準備が必要な残り項目**:
- `.env`にBinance Spot/Futures両テストネットのAPIキーを発行・設定し、
  `live/check_and_trade_carry.py --live`で実際にテストネット注文(成功/片方失敗の
  両方)が想定通り動くことを確認する
- 現物・先物ウォレット間のポートフォリオマージン設定(証拠金効率とヘッジ時の
  追証リスクに直結)を、利用する取引所の実際の仕様で確認する
- コスト前提(現状15〜30bps相当)を、実際に使う取引所・アカウントの手数料ティアで
  検証し直す
- 十分な期間、テストネット/ペーパートレードで運用し、想定通りの動きになるか確認する

## セットアップ

```bash
python -m venv .venv
.venv/Scripts/pip install -r requirements.txt
```

APIキーが必要になった場合は `.env` に置く(gitignore済み)。マーケットデータ取得自体は
公開エンドポイントのみを使うため、当面はAPIキー不要で進められる。
